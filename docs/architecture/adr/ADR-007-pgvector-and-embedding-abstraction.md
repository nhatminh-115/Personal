# ADR-007: pgvector Long-Term Memory Persistence and Provider-Neutral Embedding Layer

## Status
Accepted

## Context
In Phase 1, memory concepts were separated into five distinct cognitive tiers (Working, Episodic, Semantic, Profile, Project), but vector embeddings for semantic and project memory were stored as unindexed JSON arrays without actual vector search capabilities.
As AURA transitions into a persistent personal-agent platform in Phase 2:
- Semantic and project memory require genuine nearest-neighbor vector similarity retrieval.
- PostgreSQL production environments must leverage the native `pgvector` extension with vector indices (HNSW/IVFFlat) for performance and cosine similarity operations (`<=>`).
- Lightweight local environments (SQLite) must be supported without requiring external Postgres daemons during unit tests.
- Vector generation must be provider-neutral and decoupled from vendor SDKs, with strict validation preventing silent vector dimension or model mismatches.

## Decision

1. **Dual-Engine Persistence Strategy via Repository Abstraction:**
   - Define `SemanticMemoryStore` abstract contract providing `store()`, `search()`, `supersede()`, `archive()`, and `delete()`.
   - Implement `PgVectorSemanticStore` using `pgvector.sqlalchemy.Vector(1536)` and native cosine distance operator (`<=>`).
   - Implement `SqliteSemanticStore` computing exact in-memory cosine similarity for fast, dependency-free development and unit testing.
   - Use `get_semantic_store(db)` factory to detect the active engine dialect automatically.

2. **Provider-Neutral Embedding Abstraction:**
   - Define `EmbeddingProvider` interface with `embed()` and `embed_query()`.
   - Implement `MockEmbeddingProvider` generating deterministic, reproducible unit vectors from SHA-256 text hashes.
   - Implement `OpenAIEmbeddingProvider` generating production vectors via OpenAI-compatible endpoints with strict dimension verification.
   - Implement `EmbeddingRouter` managing active providers, validating vector dimensions, and preventing mixing vectors generated by different models.

3. **Memory Schema Evolution:**
   - Column `embedding`: `Vector(1536)`.
   - Tracking columns: `embedding_model` (e.g. `text-embedding-3-small`), `embedding_dim` (e.g. 1536).
   - Scoping and lifecycle columns: `project_name` (indexed), `confidence`, `is_active` (indexed), `supersedes_id`, `superseded_by_id`.
   - PostgreSQL migration creates HNSW cosine index `ix_memories_embedding_hnsw` on `memories USING hnsw (embedding vector_cosine_ops)`.

## Consequences

### Positive
- Genuine semantic search powered by pgvector in production and exact cosine similarity in tests.
- Zero vendor lock-in for embedding models.
- Explicit detection of model/dimension mismatches prevents corrupted vector spaces.
- Full project scoping and clean superseding of obsolete memories.

### Negative / Trade-offs
- PostgreSQL requires the `vector` extension installed (`CREATE EXTENSION IF NOT EXISTS vector`).
- Re-embedding is required if changing the embedding model in settings.
